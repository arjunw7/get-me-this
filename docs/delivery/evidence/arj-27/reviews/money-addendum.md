# ARJ-27 money precision addendum

Date: 2026-09-30. This is a narrow amendment to Task 2 of `arj27-recovery-implementation-plan.md`; the approved plan and binding 005b brief remain historical records. The arithmetic finding already superseded Task 2's `toFixed` instruction. This addendum also supersedes its `number` formatter interface because the 005a column admits values beyond JavaScript's safe integer range.

## Boundary and chosen change

`wishlist_items.original_amount_minor` is a nonnegative nullable PostgreSQL `bigint`, paired with `original_currency` by a check constraint. Thus every integer from `0` through `9223372036854775807` is a valid stored amount. An unsafe-number guard prevents a false display after parsing, but it rejects valid rows and cannot recover digits already rounded by `JSON.parse`. Divide-then-`toFixed` also rounds safe inputs incorrectly: `9007199254740990` INR becomes `.91` instead of `.90`; `9007199254740991` KWD becomes `.990` instead of `.991`. The original amount must remain exact under 005b resolution 4. [PostgreSQL numeric types](https://www.postgresql.org/docs/current/datatype-numeric.html), [JavaScript safe integers](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER).

In `src/wishlist/data.ts`, retain the current 13 explicit snapshot columns, owner wishlist filter, both ascending order clauses, 500-row paging, and owner RLS client. Change only the amount select expression from `original_amount_minor` to `original_amount_minor::text`, in the same position and with the same response field name. PostgREST documents that `select=salary::text` emits a JSON **string** under `salary`; null stays null. This is a read-time cast, requiring no view, function, migration, elevated role, or new dependency. Keep `original_currency` selected without conversion, and keep converted-money columns absent. [PostgREST casting columns](https://postgrest.org/en/stable/references/api/tables_views.html#casting-columns).

Make the selected-row/read-model and snapshot amount `string | null`; never route the amount through `Number`, a numeric JSON token, or a JavaScript number. `formatMoneyMinor` should take a decimal string and return the existing `<major>.<fixed digits> <UPPERCASE CODE>` contract (or no decimal point for zero-digit currencies), using exact integer arithmetic or string slicing. Preserve the pinned ISO 4217 digit table and unknown-code two-digit fallback. `BigInt` may be a local calculation only; no raw `bigint` goes into a component prop, client module, JSON response, or React serialization boundary. Keep `null` amount and `null` currency as no displayed price.

Validate before formatting: require a string in canonical nonnegative decimal form (`0` or a nonzero leading digit followed by digits), parse or compare exactly, and bound it to `9223372036854775807`. A number, raw `bigint`, negative/fractional/exponent string, out-of-range string, or mismatched null pair is an invariant failure. Fail into the existing generic wishlist error path; never display a rounded, invented, or partially rendered original price. Do not silently accept even a safe numeric JSON token, since that would mask a broken cast contract.

The installed `@supabase/supabase-js` and `@supabase/postgrest-js` are both 2.117.2 (`package.json`, `node_modules/.pnpm`). Its select-query parser explicitly recognizes `field::type` (`src/select-query-parser/parser.ts`), maps a cast field to its TypeScript cast type (`result.ts`), and maps `text` to `string` (`types.ts`). Its response builder uses ordinary `JSON.parse` (`src/PostgrestBuilder.ts`), so a raw numeric JSON token would still lose precision. The selected cast supplies a quoted JSON string *before* that parse; the implementation must type-check the runtime value rather than trusting an assertion cast.

## Required regression proof

1. **Pure formatter tests (`src/wishlist/display.test.ts`):** assert `2499` INR → `24.99 INR`, `3500` JPY → `3500 JPY`, `0` INR → `0.00 INR`, `9007199254740990` INR → `90071992547409.90 INR`, `9007199254740991` KWD → `9007199254740.991 KWD`, `9007199254740993` INR → `90071992547409.93 INR`, and `9223372036854775807` INR → `92233720368547758.07 INR`; supply **strings** for every amount. Retain CLP/UGX zero-digit, JOD/TND three-digit, and unknown-code fallback tests. Assert rejection of wrong types and malformed or out-of-range strings. Update row-to-snapshot tests to prove exact string and null propagation.
2. **Read contract tests (`src/wishlist/data.test.ts`):** assert every paged item query selects the same 13 original fields with `original_amount_minor::text` and no converted fields, and retains owner filter, both order clauses, and range calls. Feed string amounts above the safe limit and nulls through the mapper without conversion. A wrong-type amount or mismatched null pair must produce the generic failure, never a plausible price or partial success.
3. **Actual API JSON boundary in the CI database job (`tests/e2e/wishlist-local.spec.ts`, already included by `scripts/e2e-local-stack.sh`):** create disposable owner fixtures with original amount values supplied as **decimal strings** `9007199254740993` and `9223372036854775807`, plus a null-price row. Read via the same authenticated `supabase-js`/PostgREST `select=...original_amount_minor::text...` path used by `getOwnWishlist`; assert `typeof` is `string`, exact digits survive the HTTP JSON response, and null stays null. Render `/wishlist` and assert exact `90071992547409.93 INR` and `92233720368547758.07 INR`, the correct uppercase code, and no price for the null row. Inspect the response body or intercepted fetch response to confirm the two amount values are quoted JSON strings, rather than merely comparing already parsed values. Clean up fixtures in `finally`. Keep the existing second-user isolation assertion for this owner read. This test must run in the named CI `database` job, not only as a skipped local spec or a mocked mapper test.
4. **Wrong-type fail-closed render test (`src/wishlist/wishlist-card.test.tsx` or server read test):** inject a numeric `9007199254740992` or malformed string at the read boundary and assert no original-price text is shown and the generic error behavior is reached. A numeric guard alone is not acceptance for valid stored `bigint` rows.

Run focused tests, type-check, `pnpm verify`, and the CI database job on the final committed head. Independent code review should inspect the exact selected cast, runtime validation, serialization boundary, null/currency behavior, and both large-value API assertions before treating the recovery as complete.
